# 剩餘三個過大檔案:為什麼沒有跟著拆

`docs/decisions/props-file-split.md` 記錄了 `props.ts` 的拆法。當時盤點還有
三個過大檔案(`build-map.ts` ~4395 行、`layout-maps.ts` ~2507 行、
`game-loop.ts` ~1711 行),Zeppelin 2026-08-26/27 邀請繼續拆,這份筆記記錄
2026-08-27 實際檢查後的結論:**這三個先不拆**,以及各自的原因,給之後接手
的人(不管是 Codex 還是我自己下次)一個依據,不用重新調查一次。

## `props.ts` 為什麼好拆,是對照組

`props.ts` 的 80 個 top-level function 彼此幾乎是獨立的 factory(給座標/參數
進去,回傳一個 `THREE.Group`),沒有 module-level 的執行順序依賴——照函式邊界
切開、放進不同檔案,語意完全不變。這是「照函式切」這招管用的前提。

## `build-map.ts`、`game-loop.ts`:單一巨型函式,不是「很多函式」

```
build-map.ts: buildMap()   245 → 3774 行(整個檔案 4395 行裡佔了 3530 行)
game-loop.ts: animate()    269 → 1711 行(整個檔案 1711 行裡佔了 1440 行)
```

這兩個檔案「行數很大」不是因為裡面塞了很多獨立函式,而是幾乎整個檔案就是
`buildMap()`/`animate()` 這一個函式的函式體,裡面是大量共用同一組區域變數、
彼此順序相依的邏輯(蓋地圖的每個 map 分支互相寫入同一份場景登記表;每幀更新
的每一段互相讀寫同一組畫面/角色狀態)。

這種結構沒有「檔案邊界」可以照抄——要拆,必須先看懂這個大函式內部哪些區塊
真的彼此獨立、哪些共用了同一個閉包變數,再把要抽出去的區塊改寫成獨立函式、
把用到的區域變數改成參數/回傳值傳遞。這是需要理解語意的重構,不是搬檔案,
出錯的話會是「地圖蓋到一半漏了一塊」或「每幀更新順序跑掉」這種難抓的 bug,
風險跟工作量都遠高於 `props.ts` 那種機械式搬移。**目前判斷不值得冒這個險去
換取「檔案變小」這個好處,先不動。**

## `layout-maps.ts`:不是純資料,是一長串「邊算邊改」的腳本

表面上看有 71 個 top-level 宣告,乍看很像 `props.ts` 的模式,但實際讀過內容
後發現不是——這個檔案是**一整串由上到下依序執行、彼此互相依賴前面結果的
imperative 程式碼**,不是一堆互相獨立的常數:

- `LAYOUT`(大型巢狀設定物件)先宣告。
- 接著呼叫 `shiftMapLayout()`(從 `map-shift.ts` import)**就地修改**
  `LAYOUT.oldVillage`、`OLD_VILLAGE_RAILS`、`MAPS.oldVillage.tiles` 本身
  (西擴 100 格、南擴 100 格、港口東擴 50 格)。
- 再往下是一長串手動塗格子的迴圈(北側沙灘、東側海灘、山門、女神祠堂步道
  ……),每一段都直接改寫 `MAPS.livingArea.tiles`/`MAPS.oldVillage.tiles`
  這個共用陣列,而且是疊加式的(後面的塗改是疊在前面塗改完的結果上)。
- 最後一段才是真正「派生常數」(`FARM_ORIGIN`、`CARPENTER_HOUSE`、
  `carpenterQuest`……),這些是讀取前面已經處理完的 `LAYOUT`/`MAPS` 算出來的。

換句話說,這個檔案的「執行順序」本身就是邏輯的一部分,跟 `MAP_SHIFT_REGISTRY`
之類東西一樣是先後接力的關係。理論上可以用「單一切點、前半留在一個檔案、
後半放進 import 前半的另一個檔案」這招安全地拆(ES module 保證 import 的
模組會先整個跑完,執行順序不會亂),但:

1. 切點要挑得夠仔細,不能切在某段迴圈/IIFE 中間,而且要逐一確認後半段用到
   的每個前半段名稱都有正確 export/import——這份檔案的耦合密度比 `props.ts`
   高很多,漏抓一個名稱就是編譯錯誤,漏抓一個「隱性依賴前面 tiles 陣列已經
   長成某個形狀」的假設則是編譯過但執行結果錯,tsc 抓不出來。
2. 拆完只是把同一串邏輯攤在兩三個檔案裡,找東西時反而要在檔案之間來回跳,
   對「好找」這個原始目的的幫助有限——不像 `props.ts` 拆完之後每個新檔案
   真的是一個獨立主題(自然物/建築/裝飾/資源)。

**先不拆**,除非之後這個檔案本身變成頻繁要改、找起來真的很痛的瓶頸,再回頭
評估值不值得做這件事。

## 結論

這一輪只拆了 `props.ts`(已完成,見 `props-file-split.md`)。其餘三個大檔案
維持原樣,不是懶得拆,是拆的收益(檔案變小、好找)在這三個檔案上換不到
`props.ts` 那種低風險——真的要拆得先做語意重構(`build-map.ts`/
`game-loop.ts`)或承擔順序耦合的風險(`layout-maps.ts`)。
