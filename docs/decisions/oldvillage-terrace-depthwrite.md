# 舊城鎮台地/步道 depthWrite 穿幫問題

## 症狀

2026-08-26，Zeppelin 用新加入的第一人稱視角(`first-person-camera.ts`)在舊城鎮
(`oldVillage`)近距離貼地觀察時回報：「房子底下的部分都是空的」、「除了樓梯
的基底都不見了」、「每一層平台都有一樣的問題」。附的截圖看得到：房子/曬衣桿
之類疊在台地上的東西懸在半空，台地本身該有的實心側面(懸崖面)在某些角度直接
看穿到背景，只有樓梯階梯本身正常。

俯視的固定傾角正交鏡頭完全沒踩過這個問題——這也是這個 bug 直到新的第一人稱
視角上線才第一次被發現的原因。

## 根因

舊城鎮所有「可走的石質台地/步道」表面(`terraceMat`，涵蓋上台地、中台地、廣場
預設地面、山區降落平台，以及逐格鋪的石板步道 tile===5)都被設成
`depthWrite: false`。原本的用意寫在 `build-map.ts` 檔頭註解：避免相鄰台地/
階梯接縫處因為共平面(coincident)三角形而互相閃爍(z-fighting)。

問題是 `depthWrite:false` 的代價是「這塊東西自己從來不會把真實深度寫進深度
緩衝區」。地圖底板(`addMapFloorPatch`，永遠鋪在 y=0，整個城鎮本體一路鋪到底)
先畫、正常寫深度；台地(`renderOrder=1`)疊在上面畫，但深度緩衝區裡留著的還是
底下那片 y=0 地板的深度值；房子/道具(`renderOrder=2`)最後畫，深度測試比對到
的也是那個「地板的深度」，不是台地真正的深度。

從正上方俯視時，這個誤差幾乎不會被注意到——俯視角度下地板跟台地的深度差距
夠大，測試結果通常還是對的。但第一人稱視角貼近地面、常常是接近水平的掠射角
看向台地側面，掠射角本來就是深度緩衝精度最差的情況，這時候「深度緩衝區其實
記的是地板、不是台地」這件事就會直接讓玩家看穿本來該擋住視線的台地側面/房子
地基，變成畫面上一塊空的。

## 修法

把 `terraceMat`（`build-map.ts` 裡宣告的位置）跟逐格步道(tile===5，
`mapName === "oldVillage"` 分支)的 `depthWrite: false` 全部換成
`polygonOffset: true, polygonOffsetFactor: -1, polygonOffsetUnits: -1`。

polygonOffset 是同一類問題(共平面 z-fighting)的另一種標準修法：把表面在深度
上稍微推近鏡頭一點點，贏過跟它共平面的相鄰面，但深度緩衝區還是會正常寫入
真實深度——後面畫的東西才會被正常擋住，不會再出現「看穿地板」的穿幫。

## 尚未完全排除的部分

北灘神社平台(`northBeachPlatform`，`northPlatformWallMat`/`northPlatformTopMat`)
本來就沒有設 `depthWrite:false`，理論上不該踩到同一個問題——但 Zeppelin 的
回報是「每一層平台都一樣」，還沒確認是不是也包含神社平台。這次先修
`terraceMat`/步道兩處最明確、最大範圍的成因，如果重新測試後神社平台那邊還是
有一樣的穿幫，需要另外查一次(可能是不同的成因，例如平台跟玄武岩柱群/扶手
之間的接縫，或渲染順序的其他問題)。

`tsc --noEmit` 已跑過確認乾淨；這個修法純粹是材質屬性調整，沒有動到任何座標/
高度計算邏輯，理論上不影響碰撞/走位。實際視覺效果需要 Zeppelin 在遊戲裡重新
確認。

## 後續修正(2026-08-26 同一輪)

修完 depthWrite 之後 Zeppelin 實機重測，主要「房子底下空的」確認修好，但抓到
三個獨立的小問題，跟 depthWrite 無關，是另外三個各自的成因：

1. **(130,25) 樓梯底下是空的**：`townWestX+3` 那塊 groundElevation 台地
   (`build-map.ts` 的 Box B)刻意跳過西側中段樓梯(`westStairs[2]`,
   fromZ19~26)佔用的西緣三格，理由是怕跟樓梯階梯的實心 box 互相穿插。
   但樓梯每一階的 box 只從 `baseElevation`(=1)往上蓋，`baseElevation`
   本身到 y=0 之間完全沒有東西——那塊被跳過的西緣三格因此是真的鏤空。
   補了一塊只墊到 `baseElevation` 高度、範圍精確對齊樓梯 x/z 的地基
   (`build-map.ts`，`midWestStair` 那段)，z 從 20 開始(不是 19)避免跟
   上面的 middle 台地重疊出雙層幾何。

2. **(130,7-9)(130,17-19)(130,27-29) 扶手貼到外牆**：西緣扶手
   (`OLD_VILLAGE_RAILS` 裡 x=29.5 那條)原本是一整段 z:7~33，沒指定
   `elevation`，逐點呼叫 `oldVillageGroundY(29.5,z)` 決定高度。三段
   樓梯之間的平台銜接處不在任何樓梯的 fromZ~toZ 範圍內，會落到
   `oldVillageGroundY()` 最前面「x < westBeach.width(30) → 回傳 0」的
   早退判斷——x=29.5 剛好卡在邊界上，扶手因此整段塌到海平面。**沒有
   改 `oldVillageGroundY()` 本體**(牽動範圍太大，而且西灘那條邊界判斷
   刻意不留容許值，函式內有註解說明原因)，改成把 `layout-maps.ts` 裡
   那一條長扶手拆成 6 段：樓梯範圍內維持原樣(不填 elevation，繼續逐點
   跟階梯爬升)，三段銜接處各自明確填對應台地高度。

3. **所有扶手都懸空沒接地**：`build-map.ts` 扶手柱子(`CylinderGeometry`)
   中心點在 `ground+0.43`、高度只有 0.7，底面其實停在 `ground+0.08`，
   一直沒真的碰到地面。把高度拉到 0.86(中心點不變)，底面正好落在
   `ground+0`。

三個修法都只動局部幾何/材質參數，沒有動到共用的高度計算函式，`tsc
--noEmit` 乾淨。`map-transitions.test.ts` 裡有一段用
`OLD_VILLAGE_RAILS.filter(rail => rail.elevation === platform.elevation)`
比對北灘神社平台扶手——新拆出來的其中一段扶手 elevation 剛好也是 3(跟
`terraces.upper.elevation`/`northBeachPlatform.elevation` 同值)，混進了
這個 filter，但測試只用 `.some()` 找特定座標、沒有用數量比對，不受影響。
(2026-08-27 更新：這個環境曾經跑不動 `npm run test:map-tools`——
`node_modules` 裡的 `esbuild`/`rollup` 平台 binary 是 win32-x64，執行環境
是 linux-x64，是既有的環境問題，不是這次改動造成的。已經在這個環境重新
`npm install` 一次，補齊 linux-x64 binary 後恢復正常，見
`docs/decisions/dev-environment-notes.md`。重新用測試跑過一次後，抓到
`map-transitions.test.ts` 裡有一段「舊城鎮西側與南側各擴充 100 格海面」的
快照斷言還停在 `northBeachPlatform.segments` 的 `{x:97,z:29,width:7,depth:3}`
舊值——這正是這份文件「第三輪修正」把 `depth` 改成 `2.5` 之前的數字，測試
在那次改動當下沒能跟著跑（因為當時測試整套跑不動），現在補上
`depth: 2.5` 讓斷言跟實際程式碼一致，32 個 map-tools 測試全數通過。)

實際視覺結果一樣需要 Zeppelin 在遊戲裡重新確認。

## 第三輪修正(同一天，Zeppelin 又抓到 3 個)

上一輪修完後 Zeppelin 馬上又測出三個問題，都是同一類「台地方塊跟樓梯候選
範圍沒對齊」的變體：

1. **上/中台地把往廣場的樓梯蓋住了(x 到 155 一帶)**：`plazaStairs[0]/[1]`
   的候選判定範圍是 `fromX-0.5 ~ toX+0.5`(=54.5~58.5，兩段樓梯 fromX 都是
   55)，但上台地/中台地原本整塊鋪到 `westEdge+0.5`(=58)，會蓋過樓梯
   fromX(55)到 westEdge(57.5)之間那一大截，把階梯的立體幾何蓋成一片同高
   平面。改成把上/中台地各自拆成兩塊：樓梯所在的 z 範圍(上台地
   z:6.5~9.5、中台地 z:15.5~19.5)縮寬到 `plazaStairsFromX`，其餘 z 範圍
   維持原本鋪到 westEdge(沒有樓梯，縮寬反而會鏤空)。

2. **(129,26) 底下還是空的**：上一輪補的那塊 backfill(西側中段樓梯下方)
   z 算錯了——`addTerrace` 的 z/depth 換算成實際世界座標時，中心點是
   `z+(depth-1)/2`，實際涵蓋範圍是 `[z-0.5, z+depth-0.5]`，用
   `depth=toZ-fromZ`(=6)只蓋到 `[19.5,25.5]`，比樓梯真正的候選範圍(到
   26.5)少了最後 1 格。改成 `depth=7`，蓋到 `[19.5,26.5]`，剛好跟上面
   middle 台地、下面南側 Box C 無縫交棒。

3. **Zeppelin 自己猜對成因**：「可能要用 0.5 當單位？」——沒錯，這整輪
   全部三個坑都是同一個模式：`addTerrace()`／樓梯候選判定都用「中心點
   ±0.5」的 tile 邊界慣例，任何一個「鋪到哪裡」的計算只要漏算或多算這
   半格，就會跟樓梯的候選範圍卡不準，不是鏤空就是蓋過頭。之後如果再手
   動對齊台地/樓梯邊界，優先檢查兩邊是不是都用同一套 `-0.5 ~ +寬度-0.5`
   換算。

`tsc --noEmit` 乾淨。一樣需要 Zeppelin 實機重新確認這幾個點，以及順便再
巡一次其他台地接縫有沒有同類問題(北灘神社平台那邊如果還有問題，八成也是
同一個模式)。

## 第四輪修正(同一天，抓到我自己的抓錯)

Zeppelin 重測後回報 x=155 那邊還是有縫隙、(129,26) 還是空的，還多抓到一個
新的：神社南端樓梯跟平台重疊閃爍。三個都處理了：

1. **x=155 縫隙是我上一輪自己修錯方向**：`plazaStairs` 有兩種邊界，我搞混
   了。候選判定(`oldVillageGroundY` 拿來決定高度、給玩家站位用)刻意留了
   0.5 格緩衝，範圍是 `fromX-0.5 ~ toX+0.5`(=54.5~58.5)；但樓梯**實際的
   階梯 box 幾何**沒有這 0.5 格緩衝，物理範圍就是 `fromX ~ toX`(=55~58)
   整。上一輪我把台地邊界對齊到候選判定的邊界(54.5/58.5)，結果台地跟
   階梯的實體幾何之間反而空出 0.5 格真空——修了一個重疊、卻造出一個縫隙。
   這輪改對齊到樓梯的**實際幾何邊界**(55/58)：`narrowWidth` 的 `+0`
   改成 `+0.5`，`plazaStairsEndX` 的 `toX+1` 改成 `toX+0.5`。
2. **(129,26)**：這個座標本身在 x=29，已經在西灘那側(townWestX=30 以西)，
   不是地基缺口的座標，應該是站在旁邊往那個方向看。這輪連同上面 x=155
   一起修完後麻煩一併確認是不是也一起好了；如果站在(130,26)附近還是有
   縫，麻煩直接說,不用等我再猜。
3. **神社南端樓梯/平台重疊閃爍(新發現)**：南端樓梯(`westStairs` 最後一段，
   x:-1,fromZ:31,toZ:34)設計成「z=31 頂端切入平台」，樓梯的 z 邊界是精確
   的 fromZ/toZ(=31)，沒有 tile 緩衝；但平台的 `{x:-3,z:29,width:7,
   depth:3}` 這塊用一般「z±半格」tile 慣例算，實際南緣落在 z=31.5，比
   樓梯的起點(31)多蓋了 0.5 格，兩塊實心方塊疊在同一個位置(z:31~31.5)、
   同一個高度，變成 z-fighting 閃爍。把這塊平台的 `depth` 從 3 改成 2.5，
   南緣精準停在 31，不再跟樓梯重疊。

**這一輪學到的通用結論**：這個地圖裡至少有兩套「邊界怎麼算」的慣例混在
一起——(a) box/tile 慣例：中心點 `param+(size-1)/2`，實際邊界是
`param-0.5` 到 `param+size-0.5`；(b) 有些樓梯的候選判定刻意比階梯的實體
幾何多留 0.5 格緩衝(給站位用)，實體幾何本身反而沒有這個緩衝。之後手動
對齊台地/樓梯邊界時，要先確認「我在對齊的是候選判定範圍，還是實體幾何
範圍」——這兩個不一定一樣寬，這正是這一輪來回修錯的根本原因。

`tsc --noEmit` 乾淨。

## 第五輪修正(同一天，Box A 也要拆四塊 + 南側 z=30 邊界)

Zeppelin 這輪回報 (129~132,30) 跟 (134~158,30) 都還有縫——都是新的 z=30
邊界問題，跟前面幾輪不是同一個點：

1. **Box C 南緣停在 29.5，沒到 30**：`oldVillageGroundY()` 判定「z>=
   southBeach.z(=30)才算沙灘」，也就是 z 還沒到 30 之前(含 29.5~30 這
   半格)邏輯上仍是墊高地面。Box C 原本 depth=3，只蓋到 [26.5,29.5]，跟
   沙灘判定的邊界(30)之間空了半格。depth 改成 3.5，蓋到 [26.5,30]，剛好
   跟沙灘判定、跟 westStairs 最後一段(fromZ=30)無縫交棒。

2. **Box A 自己也漏了同一種問題，範圍比 (129~132,30) 大得多**：往前兩輪
   把 Box A(廣場東側，樓梯以東，z:0~20 單一一整塊)的西緣從 westEdge
   (57.5)搬到樓梯的 toX(58)，只顧到樓梯所在的兩段 z 範圍(6.5~9.5、
   15.5~19.5)，卻忘了 Box A 其餘 z 範圍(9.5~15.5、以及 -0.5~6.5)根本
   沒有樓梯，西緣本來就該對齊 westEdge，不該一起搬過去——整塊搬反而在
   沒有樓梯的地方多鑿出一條 x:57.5~58 的縫，範圍橫跨 Box A 的大半 z
   範圍(不只 129~132,30 那一小段，134~158 那段其實也是同一個洞的東側)。
   改成跟 upper/middle 台地一樣拆成四塊：沒有樓梯的 z 範圍鋪到
   westEdge，樓梯所在的 z 範圍縮進到樓梯的 toX。

這輪為了避免再手滑算錯 0.5，寫了一個小 node 腳本(`~/verify.js`，純算
邊界數字，沒有動 repo)把 upper/middle 台地四塊 + Box A 四塊 + 兩段樓梯
的實際幾何邊界全部列出來人工核對一輪，確認每個接縫都是「前一塊的終點
=後一塊的起點」，沒有縫也沒有重疊，才寫回程式碼。之後如果還要手動對齊
台地/樓梯邊界，建議一樣先列數字核對，不要單純心算——這幾輪的坑幾乎都是
心算漏看某個分支範圍。

`tsc --noEmit` 乾淨。
